## Blocking issues (T-010)

1. `src/scripts/70-field.js`, adaptive-quality block (`if(t&&E<2){p+=t;if(++b===90){if(p/90>24){…`): **the field always dies on touch/coarse devices.** On the coarse profile the loop only draws when `e-x >= 32`, so every measured `t` is ≥ 32ms. The 90-frame mean is therefore always > 24ms. After about 3s N is cut ×.6, and after about 6s `v=true` and `is-live` is removed. Eyes-on reproduced this at 375px with touch emulation (`pointer: fine` = false): `is-live` was true at 1.6s and false at 8.6s, with opacity 0.
   **Fix:** make the threshold depend on the profile. Replace `p/90>24` with `p/90>(o?24:48)`. That is 1.5× the 32ms coarse frame interval, matching the fine-profile ratio. Add a vm unit test: stub `matchMedia` to return `matches:false`, drive the rAF stub with timestamps 33ms apart for 200 frames, and assert that `is-live` is never removed.

2. `src/scripts/70-field.js`, `C()`: `*(E?.6:1)` uses `E` as "quality was reduced", but `E` is also set to `2` when the FIRST window was fast (`else E=2`). On a fast device, every resize after about 1.5s then re-fits N at 60% (spec §3.3 item 4 says re-fit to N). **Fix:** add a separate flag, e.g. `let q=0`. Set `q=1` exactly where `h.length=Math.round(h.length*.6)` runs, and use `*(q?.6:1)` in `C()`. Keep the file ≤ 4,096 bytes (currently 3,929).

## Non-blocking suggestions
- T-010 compositing cost (headless Chromium, software raster, so this is pessimistic): at 1440, rAF mean was 16.7ms with reduced motion, about 28–32ms with motion but no field (getContext stubbed to null), and about 45ms with the field. The JS itself is cheap: mean callback time 0.19ms, p95 0.7ms, max 5.7ms, and no long tasks after load. The extra cost is raster/composite of a full-hero canvas, about 1440×920, with a `mask-image`. One isolated run also tripped the adaptive kill on the fine profile (`is-live` false at about 5s); another run kept it live at 8.5s. Measure on real GPU hardware or in Lighthouse at the gate. If it is still heavy, consider dropping `mask-image` in favour of a gradient fade drawn into the canvas once per frame (one `fillRect` with `globalCompositeOperation='destination-out'`).
- T-010 visual: in dark theme the field is very faint (link alpha .08–.32 on `--brand` over a violet background). Light theme reads much stronger. The shockwave ring is barely visible at 150ms (T-007 restarts the mark assembly on the same click, so the mark is gone in that frame). If the owner wants more "wow", raise the dark-theme link alpha or use a lighter brand tint for links in dark. That is a spec/UX decision, not a code defect.
- T-010: the link loop recomputes every pair's distance 4 times (once per bucket). Compute each pair once, `moveTo/lineTo` into 4 `Path2D`s, and stroke each. At N=70 that is 2,415 hypot calls instead of 9,660.
- T-010: `wow-field.test.mjs` does not cover the running loop (rAF/IO stubs). Add one vm test with fake `requestAnimationFrame`, `IntersectionObserver` and `setTimeout`, and assert `is-live` after start and no rAF while `motion-paused`.
- T-017: at ≥1024, `.about__fact dd { flex: 0 1 45% }` leaves a wide gap between value and label (see shot). `flex: 0 0 auto; min-width: 9ch` would look tighter. Cosmetic.
